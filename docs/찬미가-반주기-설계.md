# 찬미가 반주기 설계서

> 목표: *"시골 할머니들의 음정·박자에 맞춰 가는 반주기"*
> 음정과 박자를 **따로따로** 낮추고 늦출 수 있는 미니플레이어.

작성 2026-08-02 · 상태: 설계(미구현)

---

## 1. 먼저 확인한 사실

설계를 바꿔 놓는 사실 하나를 먼저 적는다.

**현재 악보는 PNG 이미지다.** `.cmp` 파일은 zip이고 그 안에 `1.png`, `2.png` … 곡 번호마다
그림 한 장이 들어 있다(`hymnImageUrl()`). 가사는 `.bdb`(SQLite)의 `hymnal` 테이블에
`chapter · title · htext`로 들어 있다.

즉 **앱은 지금 "이 곡이 무슨 음으로 되어 있는지"를 전혀 모른다.** 그림과 글자만 있다.
따라서 악보에서 반주를 만들어 내는 길은 없고, **음원은 새 자료로 따로 들어와야 한다.**

이것이 아래 모든 판단의 출발점이다.

## 2. 핵심 난제 — 음정과 박자를 따로 움직이기

| 방식 | 음정만 | 박자만 | 비고 |
|---|---|---|---|
| `audio.playbackRate` | ✗ | ✗ | 둘이 **같이** 움직인다. 느리게 하면 소리도 같이 낮아진다 |
| 오디오 + 타임스트레치 DSP | ○ | ○ | 가능하지만 소리가 상한다. CPU도 먹는다 |
| **MIDI 연주** | ◎ | ◎ | 정확하고 무손실. 음 번호에 ±n, 시간축에 ×n |

녹음된 MR(mp3)에서 음정만 내리려면 **위상 보코더(phase vocoder)** 같은 신호처리가 필요하다.
`SoundTouchJS`나 `phaze` 같은 라이브러리로 되긴 하는데, 반음 3개쯤 내리면 소리에 물기가
돌기 시작하고, 4~5개를 내리면 확연히 뭉개진다.

그런데 **할머니들에게 필요한 폭이 정확히 그 지점을 넘는다.** 보통 원조보다 **2~4반음 낮게,
10~25% 느리게**가 필요하다. 오디오 방식이 가장 못 견디는 구간이 바로 우리에게 제일 중요한
구간이다.

> **결론: 이 반주기의 본체는 MIDI여야 한다.**

## 3. 두 갈래 설계

### 갈래 A — MIDI 반주기 (본체, 권장)

곡마다 `.mid` 한 개. 재생할 때 음 번호와 시간을 계산해서 소리를 낸다.

- **음정**: 모든 음 번호에 `+n` (n = 반음). 정확하고 손실 없음
- **박자**: tick→초 환산에 배율. 정확하고 손실 없음
- **크기**: 곡당 5~20KB. 645곡 다 해도 5MB 안쪽
- **저작권**: 찬송가 *가락*은 대부분 공유 저작물이다. 특정 연주를 녹음한 음반과 달리,
  가락을 MIDI로 옮긴 것은 배포 부담이 훨씬 가볍다. (편곡에 창작성이 있으면 그 편곡은 별개)
- **덤으로 되는 것들**: 멜로디 성부만 크게(따라 부르기 쉽게), 한 소절 반복,
  전주만 듣기, 특정 마디로 이동 — 진짜 반주기가 하는 일들

**소리를 내는 방법**은 세 가지를 검토했다.

| 후보 | 소리 | 용량 | 오프라인 |
|---|---|---|---|
| OscillatorNode 직접 | 장난감 같음 | 0 | ○ |
| **WebAudioFont** | 피아노·오르간 쓸 만함 | 악기당 100~300KB | ○ |
| js-synthesizer(fluidsynth wasm) + .sf2 | 가장 좋음 | wasm+음색 3~6MB | ○ |

반주기는 **음을 정확히 들려주는 것**이 목적이라 화려한 음색이 필요 없다.
피아노와 오르간 두 가지면 충분하므로 **WebAudioFont**가 무게 대비 적절하다.
(`lib/`에 jszip·sql.js를 직접 담아 쓰는 지금 방식과도 맞는다. CDN은 쓰지 않는다.)

### 갈래 B — 녹음된 MR (보조)

사용자가 이미 가진 mp3를 곡 번호에 붙이는 길. 이미 매일찬양에 mp3를 다루는 바탕이 있다.

- 음정·박자는 `SoundTouchJS`(AudioWorklet)로 처리
- **폭을 좁혀서 제공한다**: 음정 ±3, 박자 0.8~1.25배. 그 밖은 막는다.
  넓게 열어 두고 소리가 뭉개지는 것보다, 되는 만큼만 정직하게 여는 편이 낫다
- 저작권 때문에 **앱에 담아 배포하지 않는다.** 사용자가 자기 파일을 넣는다

### 음원을 고르는 순서

```
사용자가 붙인 mp3  →  번들 MIDI  →  없음(버튼 흐리게 + "음원 없음")
```

## 4. 저장 구조

지금 쓰던 그릇을 그대로 넓힌다. 새 그릇을 만들지 않는다.

| 자료 | 형식 | 저장 위치 |
|---|---|---|
| 가사 | `.bdb` SQLite `hymnal` 테이블 | `BdbStore` (기존) |
| 악보 | `.cmp` zip 안 `<번호>.png` | `BdbStore` (기존) |
| **MIDI** | **`.hmid` zip 안 `<번호>.mid`** | **`BdbStore` (같은 방식으로 추가)** |
| **사용자 mp3** | 파일 하나씩 | **`bible-praise-audio` IndexedDB (기존)** |

`.cmp`를 읽는 코드와 `.hmid`를 읽는 코드가 사실상 같으므로, 파일 확장자만 늘리면 된다.
설정 › 성경 DB 관리에 이미 있는 불러오기 화면을 그대로 쓴다.

곡별 설정(그 할머니의 305장 키)은 `localStorage`에 남긴다:

```
bible-hymn-tune = { "305": { pitch: -3, tempo: -2 }, ... }
```

## 5. 화면 (첨부해 주신 그림 그대로)

```
┌──────────────────────────────────────────┐
│  ∨   2. 성부와 성자 성령                  │   ← 접기 / 곡 번호·제목
│                                          │
│  0:00 ●━━━━━━━━━━━━━━━━━━━━━━━━━ 0:00     │   ← 탐색 막대
│                                          │
│  ( ▶ )   ( 🔁 )                          │   ← 재생 / 구간반복
│  ──────────────────────────────────────  │
│  음정  ▼   0   ▲      박자  ◀   0   ▶     │   ← 여기가 핵심
└──────────────────────────────────────────┘
```

- **음정**: -6 … +6 (반음). `0`은 원조. 화면에는 `-3` 처럼 숫자로만 — 조 이름(Eb 등)은
  할머니들께 오히려 어렵다
- **박자**: -5 … +5 단계 → 0.75배 ~ 1.4배. 한 단계 약 5%
- **누르는 곳을 크게**: 손이 떨려도 눌리도록 최소 44×44pt
- **한 번 맞춘 키는 그 곡에 남는다** — 다음에 305장을 열면 -3이 그대로 있다.
  매번 다시 맞추게 하면 반주기가 아니라 숙제가 된다
- 악보를 보면서 조작할 수 있게 **악보 화면 아래에 붙는다**(접기 가능)

## 7. 솔직하게 남는 위험

1. **MIDI 자료를 구할 수 있는가.** 이 설계 전체가 여기에 달렸다. 통일찬송가 MIDI는 흔하지만
   재림찬미가는 덜 흔하다. 없다면 갈래 B(사용자 mp3 + 제한된 음정·박자)로 물러서야 하고,
   그때는 "정확한 반주기"가 아니라 "조금 낮춰 주는 재생기"가 된다. **1단계에 들어가기 전에
   실제 파일을 몇 개라도 확보해 확인하는 것이 맞다.**
2. **구형 휴대폰 성능.** MIDI 합성은 가볍지만 SoundTouch 실시간 처리는 무겁다.
   갈래 B는 기기에 따라 끊길 수 있다.
3. **APK 용량.** 이미 167MB다. 음색 파일은 필요한 두 가지만 담는다.
